# 根因链式排查与根治

错误高发的共同根源是**打补丁式修复**与**机械文本编辑**。治理手段：
根因链式排查 + 同类 bug 换库根治 + 结构化编辑。

## 一、根因链式排查（修机制不修输出）

- 从表象逐层往下找根因链（表象 → 中间环节 → 根因，逐层确认再修）
- 修"机制层"而非"输出过滤层"（过滤是治标，机制是治本）
- 把"抓取错误"与"真缺失"分离后再归因——先分清是工具没抓到还是
  目标真不存在，再决定修哪里

## 二、先验证根因再动手（防误判）

发现 bug 后先确认根因证据再改代码：

- **反例**：把无关噪音误判为目标问题，基于正则误匹配做了错误修复——
  改完才发现目标数据本身没问题
- **正例**：报告一个 bug 必须附根因证据（符号定义位置、上下文行、
  触发路径），经确认后才允许动代码

## 三、同类 bug 根治（≥2 次即换路）

规则：**一类 bug 反复出现（≥2 次）必须换开源库或写脚本根治，禁止
继续打补丁**。

- 同类解析类 bug 反复出现 → 换成该领域专用开源库一次根治（如 SQL
  解析换专用 sql 解析库）
- 语法/编译错误高度集中在"文件超行拆分"的机械切割（字符串截断、
  常量块切碎、函数丢失）→ 用结构化编辑（见下）
- 环境 workaround 重踩 ≥2 次 → 当场写入 AGENTS.md（见
  dev-crystallize-knowledge）

## 四、举一反三扩散排查（单点 → 家族）

单点修复后按形态矩阵扩展排查全部变体：

- 从单行修复扩散出同类的全部形态（如"被丢弃的语句形态"全部修复）
- "举一反三，检查场景树是否有遗漏"——检查本项目中所有同类使用点
- 从根因点全项目搜使用点，修出同类问题

## 五、代码修改用结构化编辑（禁用正则盲改）

- 代码变换走 go/ast 工具（如 dev-line-limit skill 的 asttool）或唯一锚点
  精确替换；**禁用正则/sed/python 盲改**（机械替换反复破坏代码文件）
- 批量替换必须断言"恰好命中 1 次"并核对 diff
- 每次大改/拆分后**立即编译**（go build/go vet/跑测试）再继续下一处

## 已知坑

- 语法错误集中在"拆分"动作（文件超行拆分、整段搬移）——拆完先编译
  再拆下一处，别一次拆多个文件后才检查
- 性能优化前先确认正确性产出非空（先补正确性缺口，再谈优化）
- 定位/验证用秒级小 fixture 迭代，真实仓库只用于最终验收（避免把
  AI 额度耗在大仓库上）
