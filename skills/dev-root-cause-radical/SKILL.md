# 根因链式排查与根治

复盘结论：错误高发的共同根源是**打补丁式修复**与**机械文本编辑**。
治理手段：根因链式排查 + 同类 bug 换库根治 + 结构化编辑。

## 一、根因链式排查（修机制不修输出）

- 从表象逐层往下找根因链（如 grpc 只显示 2 个 → 四环根因链；
  attr/attr_item 4 层根因逐层修）
- 修"机制层"而非"输出过滤层"（"修复（机制层，非输出过滤）"）
- 把"抓取错误"与"真 miss"分离后再归因（R55 分 5 步：21 个 miss → 0，
  无效方法只剩 2 个真无效）

## 二、先验证根因再动手（防误判）

发现 bug 后先确认根因证据再改代码：

- **反例**：把 Redis 键噪音误判为表清单问题，差点基于正则误匹配做了
  错误修复（查上下文才发现来自枚举区块，表清单全真实无需过滤）
- **正例**：报告一个 bug 必须附根因证据（符号定义位置、上下文行、
  触发路径），经确认后才允许动代码

## 三、同类 bug 根治（≥2 次即换路）

规则：**一类 bug 反复出现（≥2 次）必须换开源库或写脚本根治，禁止
继续打补丁**。

- SQL 解析 8 次形态 bug → 换 vitess sqlparser 一次根治
- 语法/编译错误高度集中在"文件超行拆分"的机械切割（raw string 截断、
  常量块切碎、函数丢失）→ 用结构化编辑（见下）
- 环境 workaround 重踩 ≥2 次（Bash、COALESCE、/tmp 配额）→ 当场
  写入 AGENTS.md（见 crystallize-knowledge）

## 四、举一反三扩散排查（单点 → 家族）

单点修复后按形态矩阵扩展排查全部变体：

- 从单行 return 扩散出 5 类被丢弃语句形态全部修复
- "举一反三，检查场景树是否有遗漏"——检查本项目中所有同类使用点
- 从 CallExpr.Pos 根因全项目搜使用点，修出 Defer/Go 一处

## 五、代码修改用结构化编辑（禁用正则盲改）

- 代码变换走 go/ast 工具（如 dev-line-limit skill 的 asttool）或唯一锚点
  精确替换；**禁用正则/sed/python 盲改**（曾造成 8+ 次 Go 文件破坏）
- 批量替换必须断言"恰好命中 1 次"并核对 diff
- 每次大改/拆分后**立即编译**（go build/go vet/跑测试）再继续下一处
- 用户金律："为什么不使用 go 去实现脚本？内部有 ast 解析"

## 已知坑

- 语法错误集中在"拆分"动作（文件超行拆分、整段搬移）——拆完先编译
  再拆下一处，别一次拆 4 个文件后才检查
- 性能优化前先确认正确性产出非空（"先补 XORM 提取，否则性能优化
  没有实际产出"）
- 定位/验证用秒级小 fixture 迭代，真实仓库只用于最终验收（避免把
  AI 额度耗在大仓库上）
