# 交付验证与验收门禁

复盘结论：**"测试全绿" ≠ "用户可用"**。单测全绿掩盖过 3 类真实问题
（prompt 超大超时、渲染失败、硬编码）；多次"已发送但不可见"的交付
（PDF 6 轮、截图 4 轮、546 个 NaN、空图交付）全部是"Go 断言全绿但
产物/浏览器行为错"。

## 一、交付前真实自检（强制门禁）

任何产物交付前：

1. **真实打开/渲染/测量**：像素/坐标/DOM 实测（PIL 像素验证揪出过
   真实渲染 bug；playwright 实测脚本纳入回归）
2. **以用户视角通读关键区块**：图能渲染吗？数据空吗？字段对吗？
   （空数据 = FAIL）
3. **不要只发"全绿"结论**——交付应附带**可打开的产物 + 明确的核对
   清单**，让非执行方也能独立复核（用户原话："wiki html 发给我"、
   "再发一次结论"）

## 二、双向核对（工具输出 vs 源码真值）

区分"工具误报"与"真 bug"：

- **源码→DB 遗漏检查**：源码里有的，产物里有没有漏
- **DB→源码 幽灵检查**：产物里有的，源码里是否真存在

实现为双向验证程序（如 4097 个 field_access 节点逐一与源码行比对、
0 个幽灵节点）。用 worktree 对比"改前 vs 改后全量结果完全一致"可
确认无回归（120496 节点 / 1790 边全量一致）。

## 三、全量穷举验证

- 对可穷举的产物做全量比对，不抽样
- 验证工具自身的判据要逐轮校正（曾 5 处判据被逐轮修正）
- 报告/发现一个 bug 时**必须附根因证据**（符号定义位置、上下文行、
  触发路径），先定位来源再修——防止基于正则误匹配的错误修复

## 四、真实大仓库验收 + A/B 对照

单测之外，用真实大型仓库做最终验收（代码索引类项目尤为关键）：

1. 在真实仓库上 init/重建基线
2. 生成"无 AI 参数"对照组 + "有 AI 参数"实验组，双份交付
3. 按固定问题对比：有哪些明显不对？如何改进？AI 在哪些地方有高杠杆？
4. 输出优化方案

效果：暴露 3 个单测测不出的真 bug，并驱动 1800×/650× 性能修复。

## 五、性能优化带基线对比、数字验收

每次性能优化必须附量化对比与"不优化项及理由"：

- "workers 4：emitFunction 5m19s → 2m0s（2.65 倍），总 5m25s → 2m5s"
- "先测量定位"：把 51.9s 拆解到三项来源再动手
- 对象池实测无收益就诚实回滚（数据说话）

## 已知坑

- 前端改动必须 playwright 实测（546 个 translate(NaN)、布局错乱 6+ 轮
  都是"编译过了但渲染错"）
- 跨会话遗留的 P0"死代码"误判会污染长期资产——验收结论要复核再落档
- 视觉/布局类：用结果约束表达（"避免节点垂直距离太远"），参数换算
  交给 AI 并要它讲清换算依据
