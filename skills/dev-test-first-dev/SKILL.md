# 测试先行开发工作流

复盘结论：**测试先行是全项目零回归事故的基石**（约 1900 行测试揪出
5 个真实生产 bug，含 2 个长期潜伏深层 bug）。

## 一、标准流程（红→绿→全量回归→push）

```
1. 写测试：先写会失败的测试（红）——断言要具体、能区分新旧行为
2. 实现：只写让测试通过的最小代码（绿）
3. 全量回归：go test -race -count=1 ./...（或项目等价命令）
4. 验证后 git push（"改完并验证完后要 git push"）
```

配套约定：设置超时/后台执行、`make test`（或等价 Makefile 目标）作为
统一入口（`go test -race -count=1 -cover ./...`）。

## 二、断言要能数值区分新旧行为

行为契约变更时，第一步改写/新增**能区分新旧行为的精确断言**：

- 反例（模糊）："节点变多了"
- 正例（精确）："分组 7 新增恰好 7 个节点"——多一个即说明是两层，
  恰好 7 个才是一层，契约无法被悄悄破坏

## 三、负例优先 + 形态矩阵

识别/判定类需求（如"识别某类调用"）：

1. 先写"**不应当识别**"的负例（如 grpc 误报后补：ctx+err 非 pb 形态
   必须排除）
2. 按**形态矩阵**枚举变体：起点×传递方式×写入形态（如同函数/跨函数/
   嵌套/闭包/对象级），每格至少一个用例
3. 实现后主动输出"当前覆盖 X/Y，未覆盖 W"请用户确认

**教训**：grpc 场景 10+ 轮往返、SQL 解析 5+ 轮、接口形态链 5+ 轮，
全部源于"形态枚举不全"——一次只做矩阵的一格。

## 四、最小复现 bug 报告（用户侧给 AI 的输入规范）

报 bug 时自带三要素，让 AI 直接实施而非排查：

1. **完整最小复现**（文件树/源码）
2. **精确根因定位**（文件:行号 + 原因 + P0/P1 优先级）
3. **预期行为**

示例："根因在 internal/.../summary_iface.go:91 … 只识别直接的
*ssa.Const，请修复为支持间接形态。"

效果：XORM 双复现一次全绿、零返工；每次直接实施一次通过。

## 五、复杂需求：先设计树访谈再实现

收到模糊/多解需求时，用**编号问题 + 推荐答案**流程收敛：

1. AI 一次性穷举设计决策点，每个编号，附推荐答案
2. 用户一行简短作答快速拍板（如 "a c a a\n支持从路由表读取"）
3. 决策落档后实施

效果：16 问四轮收敛、设计文档一次通过、实施零需求返工。

## 已知坑

- **别把"单测全绿"当"真实可用"**——单测覆盖不了的真实问题见
  verify-and-accept；测试先行与真实验收是两回事
- fixture 行号是 AI 的机械弱点（多轮错位）——用 go/parser 动态取
  位置或"存在性"断言，别手数行号
- 接口形态链问题（mock 接口"假绿"掩盖真实形态）——单测的 mock 要与
  真实形态对齐，见 verify-and-accept 的双向核对
