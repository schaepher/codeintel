## 强制工作流（用户明确要求，任何项目适用）

1. **疑问先确认，不擅自决定**：开发中遇到设计文档未覆盖或与其冲突的点
   （阈值、数据来源、ID 格式、范围增减），先向用户说明并给出选项让其确认；
   **发现设计文档内部矛盾要报告，不静默消化**（曾因阈值 0.85 vs 0.8 矛盾
   未报告而踩坑）
2. **测试先行**：先写测试（单测+集成）→ 实现 → 执行单测 → 集成测试 →
   验证矩阵 → **验证后 git push**（推送失败先 pull --rebase）
3. **改符号前影响分析**：修改被其他符号引用的符号前，先跑影响查询
   （Go 用 codeintel/gopls；其他语言用对应工具或 grep 调用者）；影响面
   HIGH/CRITICAL 的变更须在回复中明示回归策略；**符号未索引/索引陈旧视为
   未解决，先补索引不得直接改**
4. **提交前验证（防忘机制）**：commit 前必须通过 `scripts/verify.sh
   --quick`（build + vet + 非 race 全量单测）；装 pre-commit hook
   （`scripts/install-precommit.sh`）自动执行，失败拒绝提交；hook 先跑
   `scripts/check-file-size.sh`（staged Go 文件 >300 行拒绝，提示用
   dev-line-limit skill 拆分）。全量基线（-race 逐包）手动跑
   `scripts/verify.sh`
5. **交付前主动自检 + 证据输出**：每项交付自带验证方案（真实集合从代码侧
   收集，与产物对账；噪音面显式扫描归零），验证要有证据输出（脚本
   PASS/FAIL、对账清单）贴给用户，不等用户提醒；**用户的问题往往指向更
   深的问题——先自查数据完整性，再回答表层问题**
6. **同类 bug ≥2 次即根治**：一类 bug 反复出现必须换开源库或写脚本根治，
   禁止继续逐例打补丁（SQL 解析 8 次换 vitess 一次根治的教训）；根治手段
   必须固化（依赖入库/脚本进仓库 + 加入交付检查项）
7. **形态矩阵验证**：识别/判定类功能验证必须覆盖形态矩阵（起点×传递×写入
   变体），**维度按指令全集系统枚举不能凭经验列格子**；外部依赖用真实
   模块验证不满足模拟；**功能分两层验证**（展示层 + 数据流贯通层）；
   **"设计注释"不能当事实**（每个"无法/跳过/不支持"注释都问"其实能不
   能？"）；用户报告问题时先复盘"为什么验证没覆盖该形态"，补用例再修
8. **所有命令设置超时**：`timeout N <命令>`——不能无限等待；挂起时以
   timeout 终止并定位挂起点
9. **验证用自建小示例**：/tmp 下最小 fixture（秒级）迭代，不用大仓库全量
   验证（每次数分钟成本太高）；大仓库仅用于最终验收
10. **临时脚本落盘**：一次性分析/修补脚本写入 `<项目根>/tmp/`（.gitignore
    已忽略）再执行，落盘可复用；正式工具才放 scripts/

## 常用命令（按语言/框架填写，Go 示例）

```shell
go build ./...                # 编译
go test ./...                 # 测试
scripts/verify.sh             # 全量：build + vet + -race 逐包（timeout 300s/包）
scripts/verify.sh --quick     # build + vet + 非 race 全量单测（并行 + 缓存）
scripts/verify.sh --changed   # build + vet + 增量单测（pre-commit hook 用）
make test / make it / make e2e   # 验证矩阵（-race / integration / 前端回归）
```

## 验证矩阵（改完代码三件套都要过）

- **单测**：`go test -race -count=1 ./...`（或项目等价）
- **集成**：`-tags integration`（需外部依赖时注明）
- **端到端/前端**：playwright 或等价（端口/环境自定）
- **性能改动带基线对比**：优化前后数字验收（"5m25s → 2m5s"），不靠直觉；
  CPU profile 重采样为准；对象池等优化实测无收益即回滚

## 架构原则（占位，按项目填写）

分层清晰（如 Go 的 cli 薄壳 / 业务逻辑 / 基础设施），渲染/展示留展示层；
数据模型与实现不动时只搬"命令逻辑"。设计文档权威优先，改设计先与用户确认。

## 设计流程（用户明确要求）

- **新功能/新设计先访谈**：收到模糊/多解需求时用编号问题 + 推荐答案
  逐轮访谈（设计树访谈，见 dev-test-first-dev 五节），用户确认共享理解
  再动手；纯 bug 修复/机械改动不需 full interview，但涉及行为/接口选择
  时仍先问
- **双视角必过**：任何功能设计动手前过两遍——**普通用户视角**（命令名/
  参数/默认值自然、出错信息可操作、心智模型、一条命令装上）与 **AI Agent
  视角**（契约化 --json、输出排序稳定、stale 标注可见、参数少默认合理
  支持批量、陌生仓库先概览）
- **交付前以用户视角通读产物**：生成物/渲染输出交付前像目标用户一样通读
  实际内容——不只看结构断言，逐项检查内容质量（字段名无噪音、无断裂链接、
  无空区块刷屏）

## 开发操作坑（踩过，勿重蹈——通用化）

- **改代码后忘 build 用旧产物验证**："去重没生效"类误判多源于此——改完
  代码先 build 再实测（验证顺序：test → build → 实测）
- **输出捕获管道坏**：工具输出异常（空输出/exit 1/"Stream closed"）时命令
  可能实际已执行——**重定向到文件（`cmd > tmp/x.txt 2>&1`）+ 读取文件**，
  判断真实结果以文件内容为准，不要因 exit 1 误判
- **正则/sed 盲改代码文件**：批量替换必须断言"恰好命中 1 次"并核对 diff；
  Go 代码变换走 asttool（go/ast 结构化编辑，见 dev-line-limit）或唯一锚点
  精确替换；每次大改/拆分后立即编译再继续下一处
- **手数行号**：fixture 行号是 AI 机械弱点（多轮错位）——用解析器动态取
  位置或"存在性"断言
- **fixture 断言提前 return 掩盖失败**：先收集后判断
- **嵌套 git 命令报 "index file open failed"**：pre-commit 环境下 unset
  GIT_INDEX_FILE/GIT_DIR/GIT_WORK_TREE
- **杀掉匹配自身**：`pkill -f "模式"` 会匹配自身——用精确进程名
  `pkill -x <name>`
- **临时目录配额**：大文件写 /tmp 会配额满——TMPDIR 指向仓库 `.tmp/`
  （gitignore 排除），或用 `$HOME/.tmp-build/` 兜底
- **数据库/索引无自动迁移**：改 schema 后必须重建（clean + init），否则
  旧库报错或数据形态过时误判功能未生效；serve 等持有旧文件句柄的进程
  重建后须重启

## 测试纪律

- 测试先行（先写失败测试再实现）；断言要**能数值区分新旧行为**（"分组 7
  新增恰好 7 个"而非"节点变多"）
- 负例优先：识别类需求先写"不应当识别"的用例
- 形态矩阵：起点×传递×写入按指令全集枚举，每格至少一个用例（见强制
  工作流 7）
- 断言坑：依赖 map 迭代顺序的不稳定 bug 用 `-count=10` 复现；数字断言
  注意 int vs float64（json 回读）

## 性能纪律（Q221 教训）

- **懒初始化兜底掩盖初始化遗漏**：每函数新建的处理器里出现"全量预处理 +
  nil 兜底"组合时，检查是否该提到构建级一次（曾导致 5m16s → 15.6s 的
  修复）
- **对象池收益要实测**：GC 占 CPU 时对象池看似合理，实测可能零贡献——
  性能优化以 CPU profile 重采样为准，不靠直觉；收益不足即回滚
- **驱动/依赖选型用基准数据**：cgo vs 纯 Go 等选择以基准为准，不假设
  "无 cgo 更快"

## AI 调用成本护栏（涉及真实 AI 调用时）

- 调用前声明"预计 N 次、预算 X"→ fake CLI/--dry-run 单条验证 → 全量仅
  验收跑一次
- 批量优先 + 同会话 resume 复用上下文（逐条调用曾 9/23 超时，批量 1 次
  0 失败）
- 工具白名单：不虚构工具名；自包含任务禁止查库；同一工具连续失败 2 次
  即降级，基于已有信息输出并标注置信度
- 详见 dev-ai-cost-discipline
