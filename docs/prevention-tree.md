# 事前树：防错思路树（2026-08-23，Q242–Q244 会话沉淀）

预防设计——怎么让问题不发生。由「事后树」troubleshooting-tree.md
每条排障经验反推，归纳五层：每个分支是错误发生前的一道拦截点。
排查用「事后树」；动手写代码前默读本树。

## 主干：总纲

**让错误在最早阶段暴露（fail-fast + 编译 + 断言）、让设计意图可查
（注释 + 测试锁定）、让操作有反馈（脚本断言 + 环境探针）。**

## 分支 A：动手前（选型/设计层）

拦截「技术选型返工」与「把设计当 bug」类错误（事后树主干步骤 3）：

- 技术选型先确认（MCP 手写协议被否决改 go-sdk——先访谈再动手）
- 「非显然行为」（过滤/去重/兜底/哨兵行）就地注释 why + 测试锁定，
  让设计意图可查——别人（或未来的自己）不必反推
- 设计时先列边界（多路径、多候选、截断、空结果、大小写）——测试
  矩阵先行；主路径测试测不出设计缺陷

## 分支 B：编码时（实现层）

拦截「静默失效」类错误（事后树分支 A/D3/D5）：

- fail-fast：未知 flag/参数显式报错，不留静默丢弃分支
- 写 SQL 先读 schema；关键列名常量化，不裸写字符串
- 工具作用于仓库时，先枚举仓库内容、排除自身产物目录（.codeintel/）
- 哨兵/标记行命名清晰 + 注释说明（from_col='' 是完整性判定）

## 分支 C：测试时（测试层）

拦截「测试暴露不了缺陷」类错误（事后树分支 B/D2/D4）：

- 边界行为测试先行（不只主路径）——BFS 多路径从未工作就是反例
- 写测试前读实现，了解 fallback/兜底（LIKE）与协议语义（MCP 通知
  无响应）——「等响应」前先确认对方会回
- 断言验证「路径」不只「结果」（预期走的哪条代码分支）
- 断言从可验证事实推导（输入个数在测试里显式给出，不手数）

## 分支 D：执行与验证（改代码时）

拦截「改写静默破坏」与「回归漏网」类错误（事后树分支 A/B/C/E）：

- 批量改写后立即编译（编译是最快反馈）；脚本替换带断言
  （已固化：`scripts/assert_replace.py`，默认断言恰好 1 次，
  --all/--count N 变体——runbook #10）
- 连续失败先探测环境分层，勿盲目重试
- 依赖升级独立 commit + 全量验证
- 改完跑全量基线（已固化：`scripts/verify.sh`，TMPDIR 自动切换 +
  -race 逐包 timeout；--quick 供提交前）
- **防忘机制**：`scripts/install-precommit.sh` 装 pre-commit hook——
  commit 前自动跑 check-file-size.sh（staged .go 文件 >300 行拒绝，
  提示用 dev-line-limit skill 拆分）+ verify.sh --quick，失败拒绝提交
  （硬拦截）；叠加 .claude/settings.json PostToolUse hook 提醒
  （软兜底，未装 pre-commit 的场景）

## 分支 E：环境机制

拦截「环境问题重复踩」类错误（事后树分支 A/C/F）：

- 环境约束入 memory/runbook 前置（TMPDIR、端口冲突、权限通道、
  codegraph 滞后）——开局即知，不重复踩

## 分支 F：交付验证（Q247/Q248/Q251 三次同根教训，2026-08-23 补）

拦截「检查机制给虚假安全感」类错误——有检查≠检查覆盖到位，
交付前验证不完整就交付（Q247 字段噪音 → Q248 证据机制 → Q251 空图
+ mermaid 语法错误，三次同根）：

- **检查项与产物类型绑定**：图类产物（mermaid）必须过真实渲染器
  语法检查（已固化：`scripts/mermaid-check/` jsdom+mermaid 逐个
  parse，wiki-check.py 第 7 项）；空数据显式断言（空图/空列表 =
  FAIL，不能只显示「（无…）」提示就通过）
- **交付前固定顺序，两步缺一不可**：生成 → ① 全部检查项跑完并
  看证据输出 → ② 以用户视角通读关键区块（图能否渲染 / 数据是否
  为空 / 字段名是否正常）——脚本证据不能替代通读，通读不能替代
  脚本
- **机制盲区主动探测**：建检查机制时反问「如果我是用户，打开这
  个产物哪里会让我觉得有问题」——空图、语法错误、噪音字段正是
  上次漏掉的三类
- **格式变更先验证再交付**：渲染格式/输出格式改动后，先跑真实
  解析器/渲染器验证（mermaid.parse），再交付——不要等用户指出

## 分支 G：反复 bug 根治（2026-08-23 用户明确指示）

一类 bug 反复出现时，**禁止继续逐例打补丁**——先尝试根治：

- **换开源库**：问题本质是"重新发明了某工具的本职"时，引入成熟
  开源库替代自研。实证：SQL 解析反复出错 8 次（Q220a/Q247/Q249/
  Q250/Q251）→ 换 vitess sqlparser（§84）；启发式形态 bug 由解析器
  本职解决，不再逐例补丁。
- **写脚本固化验证**：无法换库的（生成物/渲染产物）→ 写可执行检查
  脚本并绑定交付流程。实证：mermaid 渲染语法错误 → scripts/
  mermaid-check/ 真实解析器验证 + wiki-check.py 第 7 项（§83 补）；
  防忘机制 pre-commit/PostToolUse（分支 D）。
- **判据**：同类错误出现 ≥2 次即触发"换库或脚本"评估，不等第 3 次。
- **绑定**：根治手段必须固化进流程（依赖引入/脚本进仓库 + 交付
  检查项），不能只修当前实例——否则同类问题换个形态再犯。
